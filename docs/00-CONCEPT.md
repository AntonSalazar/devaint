# DevAInt — концепт v4 (concept-2)

> Статус: черновик, 2026-10-23. Предыдущие концепты (v1–v3) остались в истории git.

## 1. Питч

Выживание в духе Project Zomboid, у которого **нет собственной темы**. Ядро даёт механику:
персонажа со статами, мудлами, навыками и состояниями, мир из клеток, предметы и действия.
Всё остальное делают **моды**: сеттинг (зомби-апокалипсис, средневековье, ретро-футуризм),
угрозы (зомби, демоны, роботы), цели и правила игры.

Игра задумана как **платформа для игровых режимов**, по образцу Garry's Mod: игроки сами
ставят себе цели, собирают режимы из модов и играют вместе.

## 2. Столпы

1. **Ванилла сама является модом.** В ядре нет ни одного именованного контента: нет голода, меча
   или зомби. Всё это лежит в модах, которые грузятся так же, как пользовательские. Если
   first-party режим нельзя сделать через API модов, API нужно расширять.
2. **Мультиплеер с первого дня.** Сервер всегда главный, одиночная игра — это локальный сервер
   с одним игроком.
3. **Тело и навыки как основной геймплей.** Состояние персонажа меняет то, как он действует.
   Цепочки причин и следствий важнее боя.
4. **Безопасные моды.** Игрок, зашедший на чужой сервер, не получает на свою машину исполняемый код.

## 3. Что в ядре, а что в модах

| Ядро (C#, механизмы) | Моды (данные, Lua, ассеты) |
|---|---|
| Мир: сетка клеток, этажи, стены на рёбрах, чанки, время | Тайлы, постройки, генерация карты, смена дня и ночи, погода |
| Сущности и компоненты | Персонажи, существа, объекты мира |
| Статы, модификаторы, мудлы, навыки, состояния | Голод, жажда, боль, паника, «перегрев сервоприводов» |
| Предметы, инвентарь, контейнеры, рецепты как абстракция | Конкретные предметы и рецепты |
| Действия с длительностью (timed actions) | Конкретные действия: есть, рубить, чинить |
| Примитивы AI: восприятие (зрение, слух), цели, навигация | Поведение зомби, демонов, роботов, NPC |
| События и хуки, Lua-хост, загрузка и синхронизация модов | Правила режима, цели, условия победы и поражения |
| Сеть, сохранения, рендер, камера, ввод, базовый UI | UI-описания модов, звуки, модели, текстуры |

Правило: если у чего-то есть имя в игровом мире, это контент, и оно лежит в моде.

## 4. Архитектура

```
┌──────────── Сервер (Godot headless, оболочка) ───────────────────┐
│  Цикл тиков, ENet-транспорт, запуск sim и ModHost                │
│  ┌──────────── sim (чистый C#, без Godot) ────────────────────┐  │
│  │  Sim: мир, сущности, статы, действия, AI                   │  │
│  │  ModHost: загрузка модов, данные, Lua-песочница (MoonSharp)│  │
│  └────────────────────────────────────────────────────────────┘  │
└──────────────────────────────▲───────────────────────────────────┘
                 намерения     │     состояние (снапшоты/дельты)
┌──────────────────────────────▼─────────── Клиент (Godot 4, C#) ──┐
│  Отображение мира в 3D, интерполяция, камера, ввод, UI           │
│  Данные и ассеты модов (только безопасные форматы, без кода)     │
└──────────────────────────────────────────────────────────────────┘
```

- **Sim не зависит от Godot.** Это чистая C#-библиотека, она тестируется через xUnit.
  Состояние игры живёт только в sim, а не в узлах сцены.
- **Сервер — это тот же проект Godot**, запущенный headless (`--headless --server`), или
  отдельный экспорт dedicated server. На сервере Godot служит **только оболочкой**: цикл
  тиков, транспорт, запуск sim. Игровых узлов на сервере нет.
- **Транспорт — низкоуровневый `ENetMultiplayerPeer`** из Godot: отправка и приём байтов,
  надёжные и ненадёжные каналы, сжатие и DTLS из коробки. Высокоуровневый мультиплеер
  (RPC, `MultiplayerSpawner`, `MultiplayerSynchronizer`) не используется: он синхронизирует
  узлы, а наше состояние живёт в sim.
- **`ITransport`** с двумя реализациями: `EnetTransport` для сети и `LoopbackTransport`
  для одиночной игры и тестов. Протокол сообщений и их сериализация — наш код в sim,
  поэтому он тестируется в xUnit через loopback.
- **Одиночная игра** запускает сервер в том же процессе, что и клиент, через
  `LoopbackTransport`. Отдельного кода для синглплеера нет.

```
project/   (Godot, C#)
├── Client/      — отображение, камера, ввод, UI
├── Server/      — оболочка: цикл тиков, запуск sim и ModHost
└── Net/         — EnetTransport

sim/       (чистый C#, без Godot)
└── Sim, Defs, ModAPI, Lua (MoonSharp), протокол, ITransport, LoopbackTransport
```

- **Тик** фиксированный, **10 Гц**. Клиент интерполирует между снапшотами. Lockstep и
  rollback не нужны: темп игры медленный. Исключение — предсказание движения своего
  персонажа (раздел 6).
- **Клиент присылает только ввод и намерения**: направление движения, «начни действие X с
  предметом Y». Результат всегда считает сервер.
- **Игроков: до 32 на сервер**, лимит задаёт настройка сервера. Прикидка трафика: игрок
  видит ~200 сущностей, шлём только сдвинувшиеся, ~8 байт на сущность при 10 Гц — около
  16 КБ/с на игрока и ~0.5 МБ/с (~4 Мбит/с) исходящего у сервера на 32 игрока.

## 5. Синхронизация

Высокоуровневые RPC Godot не используются. Вместо них **свои сообщения о данных**: адресом
служит id сущности или клетка, а не путь узла.

```
СЕРВЕР                                   КЛИЕНТ
sim (правда)                             копия мира (реплика)    узлы Godot (картинка)
  │                                          ▲                       ▲
  │ за тик: «что изменилось»                 │ применить             │ событие «изменилось X»
  ▼                                          │                       │
журнал изменений ──► фильтр по чанкам ──► сообщения по ENet ──► реплика ──► WorldView
```

1. **Журнал изменений.** За тик sim записывает всё, что изменилось: сущность
   переместилась, появилась или исчезла, изменилась стена, пол или объект на клетке,
   изменился стат, начато или закончено действие.
2. **Фильтр по чанкам.** В конце тика сервер отбирает для каждого клиента изменения в
   чанках, на которые тот подписан (рядом с его персонажем), и отправляет их сообщениями.
   Частые и заменяемые данные (положения) идут ненадёжным каналом, а события (стена
   построена, действие завершено) — надёжным.
3. **Реплика.** Клиент применяет сообщения к своей копии мира. Это те же типы данных из
   sim, но без правил: только хранилище, которое поднимает события об изменениях.
4. **WorldView.** Узлы Godot подписаны на события реплики и обновляют картинку: двигают
   модели (с интерполяцией), ставят стены, перестраивают пол чанка.

**Снимок и дельты.** Когда игрок подключается или подписывается на новый чанк, сервер
сначала присылает **снимок** чанка (все клетки, стены, объекты, сущности), а дальше только
изменения. Клиент строит узлы чанка из снимка. Когда чанк выходит из зоны, клиент
удаляет его из реплики вместе с узлами.

### Роли узлов

- **Сервер:** игровых узлов нет вообще.
- **Клиент:** узлы есть, но **ничего не решают**. Любой вопрос о мире («есть ли доски?»,
  «свободна ли клетка?») задаётся реплике, а не узлу. Узел только рисует.
- UI читает статы и мудлы из реплики. Клиент может заранее затемнить недоступное действие,
  но окончательно решает всё равно сервер.
- Так как сервер не знает о дереве узлов клиента, клиент может показывать мир как угодно:
  изометрия, вид сверху, текстовый отладочный вид.

### Пример: игрок построил стену

1. Игрок A кликает по ребру клетки. Клиент отправляет намерение
   `BuildIntent(cell, side, "core:wall_wood")`.
2. Сервер проверяет материалы, навык и свободное место и запускает действие «строить».
   Клиенты рядом получают `ActionStarted(entity, action)` и показывают анимацию.
3. Действие завершилось. Sim ставит стену на ребро, в журнале появляется
   `WallChanged(cell, side, "core:wall_wood")`.
4. Все клиенты, подписанные на этот чанк, применяют сообщение к реплике. WorldView
   находит узел чанка, загружает модель стены из ассетов мода по `core:wall_wood` и ставит
   её на ребро.

```csharp
// sim: сообщения протокола
public sealed record EntityMoved(int EntityId, WorldPos To) : ServerMessage;  // дробная позиция + этаж
public sealed record WallChanged(Cell Cell, Side Side, string? DefId) : ServerMessage;

// project/Client: WorldView, обработчики событий реплики (реплика уже применила сообщение)
private void OnEntityMoved(EntityMoved m) => _entities[m.EntityId].MoveTo(m.To);

// DefId == null — стену снесли
private void OnWallChanged(WallChanged m) => _chunks[m.Cell.Chunk].SetWall(m.Cell, m.Side, m.DefId);
```

## 6. Мир

- **Сетка клеток** `(x, y, z)`, где `z` — этаж. **Клетка — 1 метр.** Клетка хранит пол,
  объекты, занятость и проходимость.
- **Стены, двери и окна стоят на рёбрах клеток**, а не занимают клетку. Так получаются
  нормальные дома с тонкими стенами.
- **Этажи:** до 8 вверх и до 2 подвалов.
- **Чанк — 32×32 клетки**, все этажи разом. Единица загрузки, сохранения, сетевой
  подписки и генерации мешей.
- **Карта конечная** и задаётся модом: до ~4096×4096 клеток (128×128 чанков). Карта —
  это контент. Процедурная генерация позже, через Lua-генератор мода.
- **Объект мира** — это сущность, привязанная к клеткам: занимает N×M клеток, имеет поворот
  (4 направления) и точки взаимодействия.
- **Время** идёт игровыми минутами внутри тика. Скорость времени задаёт режим.

### Активные и спящие чанки

- **Активная зона:** чанки в радиусе ~3 чанков (~100 м) от каждого игрока. Там всё
  симулируется полностью: AI, действия, статы, хуки Lua.
- **Зона подписки** чуть больше активной, чтобы клиент видел мир до того, как подойдёт к
  его краю.
- **Вне зон чанк спит** и не тратит процессор. Когда чанк просыпается, сервер **догоняет**
  прошедшее время: статы со скоростью изменения считаются одной формулой
  (`value += rate × elapsed`), а остальное (рост растений по стадиям, бродячие орды) —
  хуком мода `on_chunk_catch_up(elapsed)`.
- Поэтому нагрузку определяет число игроков и их разброс по карте, а не размер карты.

### Движение

- **Свободное движение** (WASD или клик по точке), позиция — дробные координаты
  `(x, y)` в метрах плюс этаж `z`. Сетка нужна миру (стены, объекты, проходимость), а не
  движению.
- **Коллизии** считает sim: тело персонажа — круг, препятствия — стены на рёбрах клеток и
  непроходимые объекты.
- **Навигация AI:** поиск пути по клеткам с учётом стен на рёбрах, затем сглаживание пути
  в свободное движение.
- **Предсказание своего персонажа на клиенте:** клиент сразу двигает своего персонажа
  по вводу той же логикой движения из sim и отправляет ввод серверу с номером. Сервер
  отвечает подтверждённой позицией и номером последнего обработанного ввода. Клиент
  сверяет, и если разошлись, исправляет позицию и переигрывает неподтверждённый ввод.
  Остальные сущности клиент только интерполирует.

## 7. Персонаж: статы, мудлы, навыки, состояния

Один общий механизм на всё. Ядро не знает, что такое «голод».

- **Стат** — число с диапазоном и скоростью изменения во времени. Пример: `core:hunger` от 0 до
  100, растёт на 0.05 в игровую минуту.
- **Модификатор** — источник, который меняет стат или его скорость: прибавкой, множителем или
  ограничением. Источниками бывают мудл, предмет, состояние или навык. У каждого
  модификатора есть владелец, поэтому его можно корректно снять.
- **Мудл** появляется на пороге стата и бывает нескольких уровней. Пример: голод выше 40 даёт
  «Голоден I», выше 70 — «Голоден II». Мудл несёт эффекты, то есть модификаторы других статов и
  скоростей действий. Именно так строятся цепочки «голод → слабость → медленнее работаешь».
- **Навык** — опыт и уровень с кривой роста из данных. Опыт начисляют действия, а уровень меняет
  длительность, шанс и качество действий.
- **Состояние** (condition) — дискретный факт о теле с собственной жизнью: рана, перелом,
  инфекция, «заражён» (из зомби-мода). Может иметь стадии и таймер, порождать модификаторы и
  быть привязанным к части тела.

Все определения задаются в данных модов. Lua нужен только для нестандартной логики через хуки.

### Как это устроено сейчас

- Значения статов — `double`: шаги за тик маленькие, у `float` ошибка заметно набегает.
- Уровни мудла — объекты с порогом и эффектами уровня:

  ```jsonc
  "moodles": [
    { "id": "core:hungry", "levels": [
        { "at": 40 },
        { "at": 70, "effects": [ { "stat": "core:fatigue", "kind": "multiply", "value": 1.5 } ] },
    ] },
  ]
  ```

- Модификаторы пока только скорости стата: `add` и `multiply`. Итоговая скорость =
  (базовая + сумма прибавок) × произведение множителей. Ограничение значения добавим, когда
  появится первый случай.
- Эффект нового уровня мудла действует со следующего тика. Порог сравнивается с допуском
  1e-6 из-за набегающей ошибки сложения.
- Id мудла уникален во всех статах. После загрузки модов проверяется: `min < max`, пороги
  по возрастанию и в диапазоне стата, эффекты ссылаются на существующие статы.
- Время по умолчанию как в Zomboid: игровые сутки за реальный час, 0.04 игровой минуты за
  тик при 10 Гц.

## 8. Действия

- **Действие** (по образцу timed action в Zomboid) состоит из проверки (можно ли начать),
  длительности, процесса (может прерваться) и результата.
- Длительность и исход зависят от навыков, мудлов и инструментов через модификаторы.
- Определение действия задаётся данными, а нестандартная проверка или результат — Lua-хуком.
- Все действия выполняются на сервере, клиент видит только прогресс и результат.

## 9. Моды

### Пакет мода

```
mods/zombies/
├── mod.jsonc         # манифест
├── data/             # определения (*.jsonc): статы, мудлы, предметы, рецепты, существа...
├── scripts/          # Lua, выполняется только на сервере
├── assets/           # glb, png, ogg — только безопасные форматы
└── locale/           # строки по языкам
```

```jsonc
// mod.jsonc
{
  "id": "zombies",
  "name": "Zombie Survival",
  "version": "0.1.0",
  "api": 1,                       // версия API ядра
  "depends": ["core >= 0.1"],
  "loadAfter": []
}
```

### Формат данных

- **JSONC** (JSON с комментариями и висячими запятыми) для всех данных: манифеста,
  определений и патчей. Разбор через `System.Text.Json`.
- **JSON Schema генерируется из C#-типов определений**, так что моддер получает
  автодополнение и проверку в VS Code.
- Моды лежат в папке `mods/` рядом с игрой, вне ресурсов Godot: Godot не импортирует их
  ассеты, а игрок видит и меняет файлы.
- Ошибки загрузки собираются все сразу. Синтаксис и неверные типы указывают файл, строку и
  путь в JSON (`mods/core/data/stats.jsonc:7: $.stats[0].rate: ...`), логические ошибки —
  файл и путь (`$.patches[2]: target core:hungerr not found`). Тексты ошибок на английском. В одном файле с ошибкой
  синтаксиса или типа сообщается только первая.

```jsonc
// mods/core/data/stats.jsonc
{
  "stats": [
    {
      "id": "core:hunger",
      "min": 0, "max": 100,
      "rate": 0.05,              // в игровую минуту
      "moodles": [
        { "id": "core:hungry", "levels": [40, 70, 90] }
      ]
    }
  ]
}
```

### Патчи

- **Идентификаторы** всегда с пространством имён: `zombies:infection`, `core:hunger`.
- **Порядок загрузки** строится по зависимостям. Мод может **патчить** чужие определения
  операциями `set`, `add`, `remove`. Полностью заменять чужой файл нельзя.

```jsonc
// mods/robots/data/patches.jsonc
{
  "patches": [
    { "op": "remove", "target": "core:hunger" },
    { "op": "set", "target": "core:fatigue", "path": "rate", "value": 0.02 },
    { "op": "add", "target": "core:pain", "path": "moodles",
      "value": { "id": "robots:sparks", "levels": [50] } }
  ]
}
```

### Режимы

- **Режим** (gamemode) — это мод или набор модов с точкой входа: правилами старта, целями,
  условиями конца. Сервер запускается с одним режимом и списком модов.

### Lua

- Реализация: **MoonSharp** (интерпретатор Lua на чистом C#).
- Выполняется **только на сервере**, в песочнице: нет файловой системы, `os`, `io`, `load`
  из строк и сети. Доступ к игре только через `ModAPI` ядра.
- **Отдельное Lua-состояние на каждый мод**: моды не видят глобальные переменные друг
  друга. Скрипты — `mods/<id>/scripts/*.lua`, выполняются по имени файла.
- **Лимит 1 000 000 инструкций** на вызов хука и на загрузку файла. Работает через
  долгоживущую корутину-диспетчер: ~2 мкс на вызов. Превысивший лимит обработчик
  отключается с ошибкой в логе; ошибка Lua пишется в лог, обработчик остаётся.
- **Библиотеки:** `string`, `math`, `table`, `bit32`, `pcall`, `xpcall`. Нет `os`, `io`,
  `load`, `require`, `debug`, `coroutine`, `collectgarbage`, `package`, `string.dump`.
  **Метатаблицы выключены**: библиотечные C#-функции вызывают метаметоды изнутри, и такой
  вызов нельзя прервать по лимиту. Включим после отдельной проверки, если понадобятся.
- `table.sort`, `string.gsub` с функцией или таблицей и `xpcall` заменены версиями на
  чистом Lua: их C#-версии вызывают Lua изнутри и обходят лимит. `string.rep` ограничен
  1 000 000 символов. `print` пишет в лог сервера с id мода.
- **Лимита памяти нет**: MoonSharp его не умеет. Один вызов ограничен инструкциями, но мод
  может раздувать таблицу от вызова к вызову. Известное ограничение.
- **Хуки регистрируются явно**: `hooks.add("stat_threshold", function(entity, moodle,
  old_level, new_level) ... end)`. Сейчас есть `tick` и `stat_threshold`; дальше
  `action_check`, `action_complete`, `entity_spawn`, `damage`, `player_join` и т.д.
- **API статов**: `stats.get(entity, id)`, `stats.set(entity, id, value)`,
  `stats.moodle(entity, id)`. Неверный id стата, мудла или сущности — ошибка Lua с текстом.
- `ModAPI` версионируется (`api` в манифесте), чтобы обновления ядра не ломали моды молча.

### Что получает клиент

- **Данные** (определения) и **ассеты в «сырых» форматах**: `glb`/`gltf`, `png`, `ogg`, `wav`,
  строки локализации. Клиент импортирует их сам во время работы.
- **Никогда:** `.pck`, `.tscn`, `.tres`, `.res`, скрипты любого вида. Сцены Godot могут
  содержать встроенный код.
- Сетевая десериализация только без объектов (`allow_objects = false`).
- **Синхронизация:** сервер присылает список модов с хешами, клиент скачивает недостающие
  (с сервера или из мастерской) и сверяет хеши.
- **UI модов:** позже, через декларативное описание (панели, полосы, списки, кнопки,
  отправляющие намерения на сервер). Клиентский код модов не планируется.

## 10. Сохранения

Сохраняет всегда сервер, в одиночной игре тоже (это локальный сервер).

### Что сохраняется

| Что | Пример |
|---|---|
| **Мета** | Версия формата, список модов с версиями, игровое время, режим, счётчик id, таблица id |
| **Чанки** | Пол, стены на рёбрах, объекты, сущности в чанке (NPC, существа, предметы на земле), время, когда чанк уснул |
| **Персонажи игроков** | Отдельно от мира, по id игрока, чтобы можно было выйти и вернуться |
| **Состояние модов** | Данные Lua-режима: «прошло 12 дней», «сработало событие X» |

### Структура

```
saves/my_world/
├── meta.jsonc             # версия, моды, время, таблица id
├── regions/
│   ├── r.0.0.bin          # регион = 8×8 чанков в одном файле
│   └── r.0.1.bin
├── players/
│   └── <player_id>.bin
└── mods/
    └── zombies.json       # состояние Lua-мода
```

- **Регионы** группируют 8×8 чанков, поэтому карта 128×128 чанков даёт не больше 256 файлов.
- **Id игрока — строка.** Пока это локальный id, позже, например, Steam ID.

### Формат

- **Мета и состояние модов — JSON**: файлов мало, их удобно читать при отладке.
- **Чанки и персонажи — свой бинарный формат** (`BinaryWriter`) со сжатием из
  `System.IO.Compression`.
- **Снимок чанка для сети и сохранение чанка — один сериализатор** с режимом «полный /
  для клиента». Полный режим добавляет данные, которые клиенту не положены (состояние AI,
  скрытые статы). Обе вещи тестируются вместе.

### Совместимость с модами

1. **Таблица id сохранения.** В бинарных файлах вместо строк (`"core:wall_wood"`) лежат
   числа, а соответствие хранится в `meta.jsonc`. Таблица своя у каждого сохранения,
   поэтому смена порядка загрузки или добавление модов ничего не ломает.
2. **Сохраняется состояние, а не определения**: «голод = 41, мудл `core:hungry` уровня 1»,
   а не скорость роста. Изменённые определения мода просто начинают действовать на старое
   сохранение.
3. **Удалённый мод или определение.** Объекты и сущности с неизвестным id **хранятся
   нетронутыми**: не участвуют в игре и не видны, но записываются обратно при сохранении.
   Если мод вернуть, всё восстановится. Мелкие данные (модификаторы, мудлы) с неизвестным
   id выбрасываются с записью в лог. Перед загрузкой игрок видит предупреждение:
   «мод `robots` отсутствует, 340 объектов будут скрыты».
4. **Состояние Lua-модов.** API `save(table)` / `load()` для JSON-совместимой таблицы со
   своей версией. При обновлении мода вызывается хук `on_migrate(old_version, data)`.
5. **Версия формата ядра** есть у меты и у каждого региона. При изменении формата пишется
   миграция «версия N → N+1» на C#, старые сохранения проходят цепочку миграций.

### Надёжность

- **Сохраняются только изменённые чанки**: когда чанк засыпает, плюс периодическое
  автосохранение.
- **Атомарная запись:** во временный файл, затем переименование. Падение сервера посреди
  записи не портит старый файл.
- **Id сущностей стабильные** (`long`, счётчик в мете), на них можно ссылаться из
  других данных («дверь заперта ключом 1042»).

## 11. Клиент: рендер и камера

- 3D-мир с **ортографической изометрической камерой** по умолчанию. Позже можно добавить
  другие режимы (свободная перспектива, вид сверху), потому что мир настоящий 3D.
- **Пол** генерируется мешами по чанкам из данных тайлов. Для прототипа подойдёт `GridMap`.
- **Стены, постройки и объекты** — 3D-модели (glb), собираются по данным клеток.
- **Срез (cutaway):** скрытие или прозрачность стен и крыш, загораживающих персонажа, плюс
  показ этажей выше текущего. Это обязательная фича изометрии.
- **Ввод отделён от камеры:** выбор клетки, движение и контекстные действия работают
  одинаково в любом режиме камеры.

## 12. First-party моды

- `core` — базовое тело (голод, жажда, усталость, боль), базовые навыки, предметы и
  действия. Сам по себе это мод, а не часть ядра.
- `zombies` — первый полноценный режим: угроза, заражение, цель «продержаться N дней». Он
  одновременно игра, демо и пример для моддеров.
- Позже второй режим в другом сеттинге (например, `robots`) как проверка, что ядро
  действительно не знает темы.

## 13. Вертикальный срез (первая цель)

1. Sim-сервер и клиент Godot в одном процессе через loopback-транспорт.
2. Маленькая карта: пол, стены на рёбрах, дверь, один этаж. Изометрическая камера, срез стен.
3. Один персонаж, свободное движение с коллизиями о стены.
4. Мод `core` (только данные): 3–4 стата, мудлы на порогах, 1–2 навыка, одно действие
   («съесть»).
5. Один Lua-хук в моде, реагирующий на порог стата.
6. Второй клиент подключается по сети (ENet) к headless-серверу и видит то же самое,
   движение своего персонажа отзывчивое (предсказание работает).

**Критерий готовности:** все шесть пунктов работают, а замена мода с данными меняет игру
без правки C#-кода.

## 14. Чего пока нет в планах

- Клиентские скрипты модов.
- Мастерская Steam (сначала моды из папки и раздача с сервера).
- Процедурная генерация больших карт (сначала маленькая карта вручную).
- Транспорт, электричество, сложная физика.
- Бой сложнее «атака / урон / рана».

## 15. Открытые вопросы

- Пока открытых вопросов нет. Закрыт вопрос о производительности Lua: замер `just bench`
  на 1000 сущностей при бюджете тика 100 мс:
  - только статы — ~42 мкс, 0.04% бюджета, без выделений памяти;
  - хук `tick`, читающий стат каждой сущности, — ~330 мкс, 0.33%, ~590 КБ памяти за тик;
  - 1000 вызовов хука `stat_threshold` за тик — ~850 мкс, 0.85%, ~2 МБ памяти за тик.
  Узкое место будущего — выделения памяти при вызовах Lua, а не время.
